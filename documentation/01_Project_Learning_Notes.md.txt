Predictive Maintenance ML System

1. Project Overview

Predictive Maintenance is a machine learning system designed to identify machines that are at risk of failure using machine operational and sensor data.

The goal is to detect potential machine failures early enough for the maintenance team to take preventive action.

2. Business Understanding
2.1 Business Problem

Manufacturing companies depend on industrial machines for continuous production. Unexpected machine failures can cause production downtime, emergency maintenance, increased maintenance costs, production losses, delayed orders, and operational risks.

A reactive maintenance approach waits until a machine fails before performing maintenance.

The company wants to move toward a predictive maintenance approach where machine data is analyzed to identify potential failures before or around the time they occur.

2.2 Current Business Process

The existing reactive maintenance process can be represented as:

Machine operates
↓
Machine develops a problem
↓
Machine fails
↓
Production stops
↓
Maintenance team investigates
↓
Machine is repaired
↓
Production resumes

This approach can result in unexpected downtime and emergency maintenance.

2.3 Desired Business Process

The desired predictive maintenance process is:

Machine operates
↓
Machine/sensor data is collected
↓
ML model analyzes machine condition
↓
Potential failure/risk is identified
↓
Maintenance team receives an alert
↓
Preventive maintenance is scheduled
↓
Unexpected downtime can be reduced

2.4 Business Objective

Develop a predictive maintenance system that uses machine operational and sensor data to identify machines at risk of failure early enough for the maintenance team to take preventive action.

The overall business goal is to reduce unexpected machine downtime, improve maintenance planning, and reduce operational losses.

Train-Test Split
-----------------
Question:

How should the dataset be divided before model training?

Objective:

Split the dataset into training and testing sets so that the model can learn from one portion of the data and be evaluated on unseen data.

Approach:

The dataset was divided into:

80% training data
20% testing data

The stratify=y parameter was used to maintain a similar proportion of failure and non-failure observations in both sets.

Why Stratification?

The target variable is highly imbalanced:

Target 0 → 96.52%
Target 1 → 3.48%

Since failure observations are relatively rare, stratification helps preserve the class distribution in both training and testing datasets.

Why Split Before Preprocessing?

The train-test split is performed before scaling or other preprocessing steps to prevent information from the test set from influencing the training process.

Preprocessing parameters will be learned only from the training data and then applied to the test data.

14. Data Preprocessing
Question:

How should the selected features be transformed before model training?

Objective:

Prepare the numerical and categorical features so that they can be effectively used by machine learning algorithms.

Numerical Features:
Air temperature [K]
Process temperature [K]
Rotational speed [rpm]
Torque [Nm]
Tool wear [min]
Categorical Feature:
Type
1. Categorical Encoding

The Type feature contains three categories:

L
M
H

One-Hot Encoding is used to convert these categorical values into numerical features.

One-Hot Encoding is preferred because the categories do not represent a numerical order.

2. Numerical Scaling

StandardScaler is applied to the numerical features.

Standardization transforms the features using:

[
z = \frac{x-\mu}{\sigma}
]

This produces features with approximately zero mean and unit standard deviation.

Why Scaling?

The numerical features have different ranges. For example, rotational speed is measured in thousands of RPM, while torque and temperature have much smaller numerical ranges.

Scaling prevents differences in numerical magnitude from disproportionately affecting scale-sensitive algorithms.

3. Preventing Data Leakage

The preprocessing transformations are fitted only on the training data.

X_train
   ↓
fit + transform
   ↓
Processed X_train

X_test
   ↓
transform only
   ↓
Processed X_test

This prevents information from the test dataset from influencing the preprocessing process.

Final Preprocessing
Feature Type	Transformation
Numerical features	StandardScaler
Categorical feature	OneHotEncoder
Unknown categories during testing	Ignored using handle_unknown='ignore'
ML Implication:

The preprocessing step converts all model inputs into a suitable numerical representation while preventing test-set information from leaking into the training process.


## 15. Handling Class Imbalance

### Question:

Is the target variable balanced between the failure and non-failure classes?

### Observation:

The target distribution is highly imbalanced:

| Target | Meaning    | Percentage |
| ------ | ---------- | ---------: |
| 0      | No Failure |     96.52% |
| 1      | Failure    |      3.48% |

Only 348 out of 10,000 observations belong to the failure class.

### Problem:

A model that predicts `No Failure` for almost every observation could achieve high accuracy while failing to detect actual machine failures.

Therefore, accuracy alone is not sufficient to evaluate the predictive maintenance model.

### Important Evaluation Metrics:

The following metrics will be considered during model evaluation:

* Precision
* Recall
* F1-score
* Confusion Matrix
* ROC-AUC

Recall for the failure class will receive particular attention because false negatives represent actual failures that the model fails to identify.

However, precision must also be considered because too many false alarms can result in unnecessary maintenance actions.

### Approach:

For the initial baseline model, class weighting will be used to give greater importance to the minority failure class.

For example:

```python
class_weight='balanced'
```

This allows the model to account for the class imbalance without artificially creating or removing observations.

### Data Leakage Consideration:

The test set will remain untouched during imbalance handling.

```text
Train-Test Split
       ↓
Training Data → Handle imbalance / class weighting
       ↓
Model Training
       ↓
Untouched Test Data → Final Evaluation
```

### ML Implication:

Because machine failures are rare, the model must be evaluated based on its ability to distinguish failure from non-failure rather than relying only on overall accuracy.

### Business Implication:

A useful predictive maintenance system should identify machines at risk while also controlling unnecessary maintenance alerts. Both missed failures and false alarms can have operational and financial consequences.

17.17. Classification Threshold and Precision-Recall Trade-off
What is a Classification Threshold?

A classification model such as Logistic Regression first produces a probability for the positive class.

In this project, the positive class is:

Target = 1 → Machine Failure

By default, a probability threshold of 0.50 is used to convert probabilities into class predictions.

Probability < 0.50 → No Failure
Probability ≥ 0.50 → Failure
Why is Threshold Tuning Important?

The default threshold is not always the best threshold for a business problem.

Changing the threshold changes the balance between precision and recall.

Lower Threshold

A lower threshold makes the model more likely to classify a machine as a potential failure.

This generally increases recall but can also increase false positives and reduce precision.

Higher Threshold

A higher threshold makes the model more conservative when predicting failures.

This can reduce false positives and improve precision, but may also increase false negatives and reduce recall.

Predictive Maintenance Trade-off

For predictive maintenance:

False Negative → Actual failure is missed.
False Positive → Unnecessary maintenance alert.

Therefore, the threshold should be selected based on the business cost of missed failures versus unnecessary maintenance.

Current Baseline

At the default threshold of 0.50:

Precision for failure = 0.14
Recall for failure = 0.82
F1-score for failure = 0.24
ROC-AUC = 0.907

The baseline model detects most actual failures but generates many false alarms.

Therefore, different classification thresholds will be evaluated to identify a more suitable precision-recall balance.
